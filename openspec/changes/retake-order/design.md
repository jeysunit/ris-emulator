# Design

## Context

- 予約は `OrderStore.add_numbered_orders` で、連番の取得・組み立て・保存を1つのトランザクションで
  作る。番号の規則は `docs/spec/04_identifiers.md` と ADR-0003・ADR-0004
- `order-status-transitions` と `mpps-scp` の後は、状態は予定・実施中・完了・取消・中止の5つで、
  完了・取消・中止は終わりの状態。終わりの状態の予約に MPPS が来たら、MPPS を記録するだけで
  予約は変えない
- 規格と IHE の出典（2026-10-23 に原文を確認）
  - IHE RAD TF-2（Rev. 23.0）4.6.4.1.2.3.3 Append Case：SPS と PPS が 1 対 N の場合。最初の PPS の後に、
    スケジュールされていない PPS を追加する。理由の例に「画質が悪い画像の撮り直し（redo）」がある。
    すべての PPS は同じ Requested Procedure と元の SPS を参照する。追加の撮影を別に予定すれば、
    それは2つの Simple Case になる、とも書いてある
  - IHE RAD TF-2x Appendix A（IHE-A.3.3）：Append Case で作る画像は、元の画像の Study Date・
    Study Time・Study Description を使う（同じ検査の中の追加）
  - PS3.3 C.4.14：Performed Procedure Step Status の DISCONTINUED は「取り消された、または
    正常に終わらなかった」
  - PS3.4 F.7.2.2.2：COMPLETED・DISCONTINUED にした MPPS は SCU が変更しない（撮り直しは新しい MPPS）

## Goals / Non-Goals

**Goals:**

- `append` と `new_order` を設定で切り替え、`new_order` では撮り直しの予約を画面と CLI で作れるようにする
- 撮り直しの予約と元の予約の関係を、RIS の中で追えるようにする

**Non-Goals:**

- MWL や HL7 で関係を相手に伝えること。DICOM の MWL には「元の予約」を表す属性が無い。
  Reason for the Requested Procedure (0040,1002) などに書く案は、臨床の理由を書く属性を別の
  用途に使うので選ばない。HL7 v2 で送る機能を作るときは、ORC-8 Parent・OBR-29 Parent の
  使い方を別に検討する
- `append` で、予約の中のシリーズの数や MPPS の数を数えること

## Decisions

### 既定は append（推奨）

IHE の Scheduled Workflow は、撮り直しを Append Case として、同じ予約・同じ Study の中で扱う
（RAD TF-2 4.6.4.1.2.3.3）。RIS は何もしなくてよく、`mpps-scp` の記録の規則だけで動く。
既定にすれば、設定を変えない利用者の動作は今と同じになる。`new_order` は施設のローカルルールの
試験のために選ぶ値にする。値の名前は、モダリティの側の設定と同じ `append`・`new_order` にそろえる。

### append で中止の予約に2つ目の MPPS が来ても、予約は変えない

最初の MPPS が DISCONTINUED で予約が中止になった後に、同じ予約で撮り直すと、2つ目の MPPS が
来ても予約は中止のまま残る。中止から実施中に戻す例外を入れる案も考えたが、`mpps-scp` の
「終わりの状態の予約には記録だけ」と食い違い、終わりの状態の意味が場合で変わる。RIS は
何もしない、という `append` の定義にも合わないので、入れない。2つ目の MPPS は記録されるので、
予約の詳細の MPPS の一覧で撮り直したことが分かる。

### 元の予約の状態（推奨は案1）

| 案 | 元が実施中 | 元が完了 | 元が中止 | 長所 | 短所 |
|----|------------|----------|----------|------|------|
| 1（推奨） | 中止にする | そのまま | そのまま | DISCONTINUED（PS3.3 C.4.14 の「取り消された、または正常に終わらなかった」）の意味に合う。終わりの状態は変えないという決まりを破らない。撮った画像が PACS にあるか（完了）無いか（中止）が状態に残る | 元が実施中のまま撮り直すと、元の MPPS の N-SET（COMPLETED）が後から来ても完了にならない（中止は終わりの状態） |
| 2 | 完了にする | そのまま | そのまま | 元の予約で撮った画像がある前提の施設に合う | 1枚も撮っていない実施中の予約まで完了になり、画像の無い完了の予約が残る |
| 3 | そのまま | そのまま | そのまま | RIS が何も決めない | 実施中の予約が MWL に残り、モダリティに元と撮り直しの2件が並ぶ |

案1を選ぶ。元の予約が完了・中止のときは、終わりの状態なので変えない。

### 撮り直しを作れる状態は実施中・完了・中止

予定の予約は、まだ撮っていないので撮り直しではない。取消の予約は検査そのものを取り消したので、
撮り直さない。

### 作成は1つのトランザクションで行う

`add_numbered_orders` に、同じトランザクションで元の予約を読む・状態を変える処理を渡せるように
する。元の予約の状態の確認、撮り直しの予約の保存、元の予約の中止への変更を、`BEGIN IMMEDIATE` の
中でまとめて行う。途中で元の予約の状態が変わっていたら（同時に取消にされたなど）、作成をやめる。

### 関係は撮り直しの予約の側に持つ

`Order` に `retake_of: str = ""`（元の受付番号）を足す。元の予約の側には持たず、詳細の画面で
`retake_of` が自分の受付番号の予約を引く。片方だけに持つので、2つが食い違うことが無い。
件数が少ないので、予約の JSON の列を `json_extract` で引く形で始める。

### 予定日時の既定は作った時点

モダリティは今日の日付で MWL を引くことが多いので、作った時点の日付と時刻（分まで）を既定に
する。CLI は `--date`・`--start` で、画面は詳細のボタンの横の入力で変えられる。

## Risks / Trade-offs

- [`append` で、中止の予約を同じ予約の中で撮り直すと、予約は中止のまま] → 上の決定のとおり。
  撮り直しの記録は MPPS の一覧に残る。予約を完了にしたい施設は `new_order` を使う
- [`new_order` で、元の予約の MPPS が撮り直しの後に COMPLETED で届く] → 元の予約は中止のまま
  （案1）。MPPS は記録されるので、予約の詳細で食い違いが見える
- [台帳（`station-registry`）が変わった後の撮り直し] → 装置の値は元の予約から写すので、
  台帳から消えた装置でも撮り直しの予約を作れる

## Migration Plan

1. 設定に `orders.retake_mode` が無ければ `append` とみなす。今の設定はそのまま動く
2. 保存済みの予約は `retake_of` を持たない（空の値で読む）
3. 戻すときは、この change の commit を revert する。撮り直しの予約は普通の予約として残る
