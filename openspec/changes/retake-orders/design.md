# Design

## Context

- 予約は `OrderStore.add_numbered_orders` で、連番の取得・組み立て・保存を1つの
  トランザクションで作る。番号の規則は `docs/spec/04_identifiers.md` と ADR-0003・ADR-0004
- `order-status-transitions` と `mpps-scp` の後は、状態は予定・実施中・完了・取消・中止の5つで、
  完了・取消・中止は終わりの状態。MPPS の DISCONTINUED で予約は中止になる
- (A) は IHE RAD の Scheduled Workflow で、撮り直しや追加の撮影は同じ Scheduled Procedure Step を
  参照する新しい MPPS とシリーズとして送られる。(B) は施設のローカルルールで、RIS が新しい予約を
  発番する。どちらの施設のモダリティも試験できるようにする

## Goals / Non-Goals

**Goals:**

- (A) と (B) を設定で切り替え、(B) では撮り直しの予約を画面と CLI で作れるようにする
- 撮り直しの予約と元の予約の関係を、RIS の中で追えるようにする

**Non-Goals:**

- MWL や HL7 で関係を相手に伝えること。DICOM の MWL には「元の予約」を表す属性が無い。
  Reason for the Requested Procedure (0040,1002) などに書く案は、臨床の理由を書く属性を別の
  用途に使うので選ばない。HL7 v2 で送る機能を作るときは、ORC-8 Parent・OBR-29 Parent の
  使い方を別に検討する
- (A) で予約の中のシリーズの数や MPPS の数を数えること

## Decisions

### 設定の値は same_study と new_order

設定の値は、撮り直しの結果を表す名前にする。`ihe`・`local` のような出どころの名前は、
施設のルールが IHE と同じ場合に読み違える。既定は `same_study` で、設定を変えない利用者の
動作は今と同じになる。モダリティの側の設定も同じ2つの値で書けるようにそろえる。

### 元の予約の状態（推奨は案1）

| 案 | 元が実施中 | 元が完了 | 元が中止 | 長所 | 短所 |
|----|------------|----------|----------|------|------|
| 1（推奨） | 中止にする | そのまま | そのまま | DISCONTINUED（PS3.3 C.4.14 の「取り消された、または正常に終わらなかった」）の意味に合う。終わりの状態は変えないという決まりを破らない。撮った画像が PACS にあるか（完了）無いか（中止）が状態に残る | 元が実施中のまま撮り直すと、元の MPPS の N-SET（COMPLETED）が後から来ても完了にならない（中止は終わりの状態） |
| 2 | 完了にする | そのまま | そのまま | 元の予約で撮った画像がある前提の施設に合う | 1枚も撮っていない実施中の予約まで完了になり、画像の無い完了の予約が残る |
| 3 | そのまま | そのまま | そのまま | RIS が何も決めない | 実施中の予約が MWL に残り、モダリティに元と撮り直しの2件が並ぶ |

案1を選ぶ。元の予約が完了・中止のときは、その後の撮り直しで状態を変える理由が無い。

### 撮り直しを作れる状態は実施中・完了・中止

予定の予約は、まだ撮っていないので撮り直しではない（予定日時を変える操作が要るなら別の
change）。取消の予約は検査そのものを取り消したので、撮り直さない。

### 作成は1つのトランザクションで行う

`add_numbered_orders` に、同じトランザクションで元の予約を読む・状態を変える処理を渡せるように
する（例：`build` に元の予約を引く関数を足す）。元の予約の状態の確認、撮り直しの予約の保存、
元の予約の中止への変更を、`BEGIN IMMEDIATE` の中でまとめて行う。途中で元の予約の状態が
変わっていたら（同時に取消にされたなど）、作成をやめる。

### 関係は撮り直しの予約の側に持つ

`Order` に `retake_of: str = ""`（元の受付番号）を足す。元の予約の側には持たず、詳細の画面で
`retake_of` が自分の受付番号の予約を引く。片方だけに持つと、2つが食い違うことが無い。
予約の表に `retake_of` の列と索引を足すか、JSON の列を `json_extract` で引くかは、件数が
少ないので後者で始める。

### same_study の例外は MPPS の N-CREATE だけに限る

`same_study` では、最初の MPPS が DISCONTINUED で予約が中止になっても、同じ予約で撮り直す。
新しい MPPS の N-CREATE（IN PROGRESS）が来たら予約を実施中に戻し、その MPPS の COMPLETED で
完了にする。手動の変更で中止から戻すことは許さない（誤操作で終わりの状態が戻らないように）。

### 予定日時の既定は作った時点

モダリティは今日の日付で MWL を引くことが多いので、作った時点の日付と時刻（分まで）を既定に
する。CLI は `--date`・`--start` で、画面は詳細のボタンの横の入力で変えられる。

## Risks / Trade-offs

- [`new_order` で、元の予約の MPPS が撮り直しの後に COMPLETED で届く] → 元の予約は中止のまま
  （案1）。MPPS は記録されるので、予約の詳細で食い違いが見える
- [`same_study` の例外で、中止が終わりの状態でなくなる場面がある] → MPPS による N-CREATE の
  ときだけに限り、spec のシナリオで固定する
- [撮り直しの予約の文字コードで、元の予約の値が書けない] → 元の予約は同じ文字コードで作れて
  いるので起きない。設定の台帳（`station-registry`）が変わっていても、装置の値は元の予約から写す

## Migration Plan

1. 設定に `orders.retake_policy` が無ければ `same_study` とみなす。今の設定はそのまま動く
2. 保存済みの予約は `retake_of` を持たない（空の値で読む）
3. 戻すときは、この change の commit を revert する。撮り直しの予約は普通の予約として残る
